# 08 死锁、条件变量与线程卡死

## 本章目标

对挂死进程进行非侵入快照，识别锁顺序反转和丢失唤醒。

## Demo

```bash
cmake --build --preset x86-debug --target deadlock_lab
./build/x86-debug/demos/08_deadlock_lab/deadlock_lab --mode lock-order &
PID=$!
```

## GDB attach

```bash
gdb -q -p "$PID"
```

```gdb
set pagination off
info threads
thread apply all bt
thread apply all bt full
detach
quit
```

也可快速采集：

```bash
gdb -q -batch -ex 'set pagination off' \
  -ex 'thread apply all bt' -p "$PID" > thread-dump.txt
```

连续采集三次，每次间隔数秒。如果调用栈完全不变且多个线程相互等待，更能支持死锁判断。

## 学员任务

找出：

1. 哪个线程持有 `device_mutex`。
2. 哪个线程持有 `queue_mutex`。
3. 两个线程分别在等待什么。
4. 为什么 CPU 接近零但程序不退出。

## 实战答案

接收线程先锁设备再等队列；控制线程先锁队列再等设备，形成环路。修复模式使用 `std::scoped_lock` 同时获取两把锁。

`lost-wakeup` 在等待者建立前发送通知，同时谓词永远为假。条件变量必须与受互斥锁保护的状态谓词共同使用；通知本身不是状态。

## 生产修复原则

- 制定全局锁顺序。
- 缩小临界区，不在锁内做 I/O、FFT 或绘图。
- 等待必须有谓词，重要路径考虑超时。
- 停止流程唤醒所有等待者。
- 调试版本记录锁等待时间和持有时间。
