# 90 NR 设备控制软件综合排障

## 项目目标

模拟以下真实链路：

```text
Qt 参数界面
  → UDP 控制命令
  → 模拟 FPGA 循环读取 30.72 Msps、10 ms 单音 IQ
  → UDP IQ 分包
  → 接收线程
  → 有界队列
  → FFT 工作线程
  → 最新频谱和指标文件
  → Qt 频谱界面
```

IQ 文件采用交织 `int16_t I, int16_t Q`：

```text
1,228,800 字节 ÷ 4 字节/复数样点 = 307,200 个复数样点
307,200 ÷ 30.72 Msps = 10 ms
```

程序启动时会检查文件大小是否为完整 IQ 对。协议头明确使用网络字节序；IQ 负载保持设备约定的二进制格式。

## 命令行正常链路

终端一：

```bash
$DIR/nr_fpga_sim --mode normal
```

终端二：

```bash
$DIR/nr_scope_app --mode normal --duration 30 \
  --interval-us 2000 --metrics metrics.csv \
  --spectrum latest_spectrum.csv
```

程序每秒输出：

```text
rx processed missing corrupt queue latency_us peak_bin
```

正常情况下：

- `received` 与 `processed` 大致同步。
- 队列接近零，峰值有界。
- `missing` 和 `corrupt` 为零。
- 延迟不会随时间单调增长。
- 单音信号的 `peak_bin` 相对稳定。

## Qt 界面

```bash
$DIR/nr_scope_gui
```

界面负责设置故障场景、包间隔和运行时长，并启动模拟 FPGA 与分析程序。频谱区读取分析线程输出的最新 FFT 结果。若没有 Qt 开发包，目标会构建成提示性占位程序。

## FPGA 故障注入

```bash
$DIR/nr_fpga_sim --mode loss
$DIR/nr_fpga_sim --mode corrupt
$DIR/nr_fpga_sim --mode reorder
$DIR/nr_fpga_sim --mode flood
```

- `loss`：每 50 包跳过一次发送。
- `corrupt`：修改负载但保留原校验值。
- `reorder`：周期性延迟一个包再发送。
- `flood`：不做发送间隔限制。

## 应用故障注入

```bash
$DIR/nr_scope_app --mode backlog --duration 60
$DIR/nr_scope_app --mode history-leak --duration 60
$DIR/nr_scope_app --mode small-buffer --duration 60
$DIR/nr_scope_app --mode crash --duration 60
```

- `backlog`：处理线程每包额外等待 5 ms，低于生产速率。
- `history-leak`：保存每一帧完整频谱，RSS 持续增长。
- `small-buffer`：socket 接收缓冲区过小。
- `crash`：处理第 1000 个有效包时触发段错误。

## 综合工单 A：延迟越来越大

现象：开始正常，随后频谱越来越滞后，CPU 没有完全占满。

### 学员任务

```bash
pidstat -p PID -t -r -w 1
ss -u -a -n -m
watch -n 1 'grep -E "VmRSS|Threads" /proc/PID/status'
```

把 `metrics.csv` 中的 `received`、`processed`、`queue` 和 `latency_us` 画到同一时间轴。

### 标准证据

若接收速率大于处理速率、队列和延迟同步上升，瓶颈在消费者。CPU 没有满不代表容量足够，消费者也可能在休眠、等待锁或串行执行。

### 修复验证

- 降低生产速率或提升算法吞吐。
- 批处理 IQ。
- 减少复制和分配。
- 设置明确的队列上限与丢弃策略。
- 修复后使用相同 `interval-us` 复测。

## 综合工单 B：RSS 持续增长

### 排查

```bash
pidstat -r -p PID 1
pmap -x PID | tail -1
heaptrack $DIR/nr_scope_app --mode history-leak --duration 30
```

若 `queue` 很低但 RSS 增长，检查历史结果持有；若队列和 RSS 同时增长，先处理背压。不能仅凭 RSS 宣布“内存泄漏”。

## 综合工单 C：偶发段错误

```bash
ulimit -c unlimited
$DIR/nr_scope_app --mode crash --duration 60
coredumpctl debug nr_scope_app
```

在 GDB 中执行：

```gdb
thread apply all bt full

```

再使用 ASan 构建复测：

```bash
cmake --preset x86-asan
cmake --build --preset x86-asan --target nr_scope_app nr_fpga_sim
```

## 综合工单 D：丢包和频谱跳变

同时采集：

```bash
tcpdump -i lo -nn -tt udp port 41001 -w iq.pcap
ss -u -a -n -m
grep -A1 '^Udp:' /proc/net/snmp
ip -s link
```

分析顺序：

```text
FPGA sequence
→ tcpdump 是否看到
→ 网卡/内核是否丢弃
→ socket queue 是否溢出
→ 应用 received/missing/corrupt
→ 业务队列是否积压
```

乱序不应简单记为大量丢包。生产实现需要独立统计缺失、迟到、重复和乱序。

## 综合工单 E：GUI 卡顿

先看 GUI 心跳，再定位线程：

```bash
top -H -p PID
pidstat -p PID -t 1
perf record -F 99 -g -p PID -- sleep 20
perf report
```

确认计算是否进入 GUI 线程、刷新频率是否与数据包频率绑定、历史点是否无限增长。GUI 应固定帧率获取最新结果，而不是逐包绘图。

## 软硬件边界判断

| 证据 | 判断 |
|---|---|
| 模拟 FPGA 已跳号，抓包也缺号 | 发送端/FPGA |
| 抓包有包，应用没有 | socket/内核/应用接收 |
| 接收完整，业务队列增长 | 软件消费者 |
| x86 正常、真实 ARM 满核 | ARM 算力或优化 |
| QEMU ARM 很慢 | 不能作为硬件瓶颈证据 |
| 目标机 IRQ/网卡 drop 增长 | 驱动、IRQ 或硬件链路 |
| CPU 降频且温度高 | 散热/硬件限制 |

## 最终提交报告

每次综合实验至少提交：

1. 软件版本、架构、构建类型和启动参数。
2. 可重复的输入与故障发生时间。
3. CPU、RSS、线程、队列、包计数和延迟时间线。
4. 至少两个被排除的假设及证据。
5. 最终根因对应的线程、函数或外部资源。
6. 修复说明。
7. 相同输入下的修复前后对比。
8. x86、QEMU ARM64、真实 ARM64 的结论边界。
